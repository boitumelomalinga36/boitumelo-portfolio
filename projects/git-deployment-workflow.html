Git-Based Laravel Deployment Workflow

A safe, repeatable release process that replaces manual FTP updates with Git branches, GitHub pull requests and one guarded production deployment script.

Purpose and outcome

FTP is useful for an initial installation, but it should not be the normal release method. Once this workflow is active, every change is recorded, reviewed and deployed consistently while the production environment stays intact.

Local change→Feature branch→PR to develop→PR to main→Deploy production
  1. Develop locally and isolate each change in its own branch.
  2. Review changes through GitHub pull requests.
  3. Deploy only the approved main branch.
  4. Keep .env, storage, uploads, public entry files and the database in place.
  5. Build frontend assets locally because the shared server has no Node or NPM.

Important: Replace every placeholder in this guide. Never publish passwords, private keys, APP_KEY values, payment passphrases, API secrets or database credentials.

  • <LOCAL_PROJECT> — local Laravel directory
  • <GITHUB_OWNER> and <GITHUB_REPOSITORY> — repository details

  • <APP_DIR> — private Laravel application directory
  • <PUBLIC_DIR> — website document root
  • <PHP_BIN> and <COMPOSER_BIN> — server executables
  • <PRODUCTION_URL> — final HTTPS URL

Branch structure and complete release flow

develop contains integrated work. main contains approved production code. Feature and bug-fix branches isolate individual changes.

feature/descriptive-feature-name
bugfix/descriptive-problem-name
docs/descriptive-document-name
chore/descriptive-maintenance-name
What this means

The word before the slash describes the type of work. The words after it describe the specific change. This makes the purpose of a branch clear before anyone opens it.

develop→feature/* or bugfix/*→PR into develop→PR into main→production

This provides two approval points: first, whether an individual change belongs in the integrated version; second, whether the complete integrated version is ready for production.

4

Prepare local Git before connecting production

Bring main up to date

Run these commands from your local project. They update develop, then compare it with main without changing either branch.

cd <LOCAL_PROJECT>
git switch develop
git pull --ff-only origin develop

git rev-list --count main..develop
git rev-list --count develop..main
git --no-pager diff --stat develop main

cd enters your project folder.

git switch changes the active branch.

git pull --ff-only downloads changes but refuses to create an unexpected merge.

git rev-list --count counts commits that exist on one branch but not the other.

If develop is ahead, open a GitHub pull request with base: main and compare: develop. Merge it, then update both local branches.

git switch main
git pull --ff-only origin main
git switch develop
git pull --ff-only origin develop

If .DS_Store blocks a branch switch

A stash safely puts an uncommitted change aside. Here it targets only .DS_Store, so your other work is left untouched.

git stash push -m "temporary local DS Store change" -- .DS_Store
git switch main
git pull --ff-only origin main
git stash list

If main was pulled while still on develop

git switch main
git pull --ff-only origin main
git branch -f develop origin/develop
git switch develop
git pull --ff-only origin develop

Use git branch -f only while develop is not checked out and after confirming the intended work exists on origin/develop.

Start and finish normal work

This is the everyday developer loop: update develop, create an isolated branch, inspect and build the work, then commit and publish the branch.

cd <LOCAL_PROJECT>
git switch develop
git pull --ff-only origin develop
git switch -c feature/<FEATURE_NAME>

git status --short
git diff
npm run build

git add .
git commit -m "feat: describe the feature"
git push -u origin feature/<FEATURE_NAME>
8

Verify and prepare the production server

Connect and check required tools

SSH opens a secure terminal session on the hosting server. The checks below only inspect the environment—they do not install or change anything.

ssh <SSH_USER>@<SSH_HOST> -p <SSH_PORT>
cd <APP_DIR>

git --version
git status
git remote -v
git branch --show-current
command -v composer || echo "Composer command unavailable"
command -v node || echo "Node unavailable"
command -v npm || echo "NPM unavailable"
command -v rsync || echo "rsync unavailable"
command -v curl || echo "curl unavailable"
<COMPOSER_BIN> --version
bash --version | head -1

command -v reports where a program is installed.

|| runs the message on its right only if the check on its left fails.

head -1 keeps the version output short.

The workflow requires Git, Bash, PHP, Composer, rsync and curl. Node and NPM are not required on production.

Check ignored production data

grep -nE '^/?(\.env|vendor|node_modules|public/build)' .gitignore

mkdir -p <HOME_BACKUP_DIR>
chmod 700 <HOME_BACKUP_DIR>

At minimum, never commit .env, vendor, node_modules, public/storage or storage runtime content. Keep backups outside both the repository and public document root.

Initialise Git safely in the existing application

git init adds Git tracking metadata to the existing folder. It does not delete the Laravel files already there.

cd <APP_DIR>
git init -b main
git remote add origin https://github.com/<GITHUB_OWNER>/<GITHUB_REPOSITORY>.git

Do not clone over the working application and do not use git reset --hard. Either action can overwrite production-specific files.

11

Authenticate with a read-only deploy key

A deploy key lets this one server read this one private repository. The public half goes to GitHub; the private half never leaves the server.

mkdir -p ~/.ssh
chmod 700 ~/.ssh
ssh-keygen -t ed25519 \
  -C "production-deployment" \
  -f ~/.ssh/application_github \
  -N ""

chmod 600 ~/.ssh/application_github
chmod 644 ~/.ssh/application_github.pub
cat ~/.ssh/application_github.pub

mkdir -p creates the SSH folder if needed.

chmod 700 allows only your server account to access that folder.

ssh-keygen creates the public/private key pair without a passphrase, which allows non-interactive deployment.

  1. Open the GitHub repository and go to Settings → Deploy keys.
  2. Add the complete public key and leave Allow write access unchecked.
  3. Test authentication, switch the remote to SSH and bind this repository to its key.
ssh -i ~/.ssh/application_github \
  -o IdentitiesOnly=yes \
  -T git@github.com

cd <APP_DIR>
git remote set-url origin git@github.com:<GITHUB_OWNER>/<GITHUB_REPOSITORY>.git
git config core.sshCommand \
  "ssh -i <HOME>/.ssh/application_github -o IdentitiesOnly=yes"
git remote -v

Display and copy only the .pub file. Never reveal or upload the private key.

12

Connect production without overwriting it

This is the careful bridge between the manually uploaded application and Git. Fetch first, then compare the repository version with the files already serving users.

cd <APP_DIR>
git fetch origin main
git reset --mixed origin/main
git status --short > /tmp/application-git-status.txt
wc -l /tmp/application-git-status.txt
sed -n '1,160p' /tmp/application-git-status.txt
git branch --show-current
git log -1 --oneline

A mixed reset associates the working directory with origin/main without replacing working files. Review every reported difference.

Why not use a hard reset?

A hard reset writes repository versions over working files. On an existing production installation that could destroy server-specific changes before you have reviewed them.

Mark deliberate production exclusions

skip-worktree is a local instruction telling Git not to repeatedly report known production-only differences. It is not committed and must be documented for future maintainers.

git update-index --skip-worktree \
  .DS_Store \
  bootstrap/cache/.gitignore \
  storage/app/.gitignore \
  storage/framework/.gitignore \
  storage/framework/cache/.gitignore \
  storage/framework/sessions/.gitignore \
  storage/framework/views/.gitignore \
  storage/logs/.gitignore

git ls-files 'tests/**' | while read -r production_test_file; do
  git update-index --skip-worktree "$production_test_file"
done

git status --short
git ls-files -v | awk '$1 == "S" {print $2}'

Never hide unexplained changes in application code, routes, migrations, configuration or dependency lock files.

Set and verify the upstream

git branch --set-upstream-to=origin/main main
git branch -vv
git log -1 --oneline

curl -sS -o /dev/null -w "Homepage: %{http_code}\n" <PRODUCTION_URL>/
curl -sS -o /dev/null -w "Health: %{http_code}\n" <PRODUCTION_URL>/health
15

Build frontend assets without Node on production

Remove /public/build from .gitignore because this server cannot run Vite. Build locally and commit the generated assets with each affected release.

Why commit generated files?

Normally Vite builds assets on the server. Here the server has no Node runtime, so your computer creates the final CSS and JavaScript bundle and Git transports that exact bundle to production.

npm ci
npm run build
ls -la public/build
ls -la public/build/manifest.json

git add .gitignore public/build
git commit -m "chore: include production frontend assets"

Do not copy a development public/hot file to production. It points Laravel to a local Vite development server.

Create the guarded deployment script

Store the script at deploy/shared-hosting-deploy.sh, replace the placeholders and make it executable.

chmod +x gives the file permission to run as a program. You normally do this once and commit the executable permission to Git.

chmod +x deploy/shared-hosting-deploy.sh
#!/usr/bin/env bash
set -Eeuo pipefail

APP_DIR="<APP_DIR>"
PUBLIC_DIR="<PUBLIC_DIR>"
PHP_BIN="<PHP_BIN>"
COMPOSER_BIN="<COMPOSER_BIN>"
DEPLOY_BRANCH="main"
HEALTH_URL="<PRODUCTION_URL>/health"
maintenance_enabled=false

restore_application() {
  if [[ "$maintenance_enabled" == "true" ]]; then
    "$PHP_BIN" "$APP_DIR/artisan" up >/dev/null 2>&1 || true
  fi
}

deployment_failed() {
  local exit_code=$?
  local line_number=${1:-unknown}
  restore_application
  printf 'Deployment failed at line %s. Maintenance mode was disabled.\n' "$line_number" >&2
  exit "$exit_code"
}
trap 'deployment_failed $LINENO' ERR

[[ -d "$APP_DIR/.git" ]] || { echo "Not connected to Git" >&2; exit 1; }
[[ -f "$APP_DIR/.env" ]] || { echo "Production .env is missing" >&2; exit 1; }
[[ -f "$PUBLIC_DIR/index.php" && -f "$PUBLIC_DIR/.htaccess" ]] || {
  echo "Public entry files are missing" >&2; exit 1;
}
[[ -x "$PHP_BIN" && -x "$COMPOSER_BIN" ]] || {
  echo "PHP or Composer is unavailable" >&2; exit 1;
}

cd "$APP_DIR"
[[ "$(git branch --show-current)" == "$DEPLOY_BRANCH" ]] || {
  echo "Production must remain on main" >&2; exit 1;
}
[[ -z "$(git status --porcelain --untracked-files=no)" ]] || {
  echo "Tracked production files contain local changes" >&2;
  git status --short --untracked-files=no >&2; exit 1;
}

git fetch origin "$DEPLOY_BRANCH"
current_revision=$(git rev-parse HEAD)
target_revision=$(git rev-parse "origin/$DEPLOY_BRANCH")
git merge-base --is-ancestor "$current_revision" "$target_revision" || {
  echo "Remote is not a fast-forward update" >&2; exit 1;
}

"$PHP_BIN" artisan down --retry=30
maintenance_enabled=true
git merge --ff-only "origin/$DEPLOY_BRANCH"
"$COMPOSER_BIN" install --no-dev --no-interaction --prefer-dist --optimize-autoloader
"$PHP_BIN" artisan migrate --force

rsync -a --delete \
  --exclude='index.php' \
  --exclude='.htaccess' \
  --exclude='storage' \
  --exclude='hot' \
  "$APP_DIR/public/" "$PUBLIC_DIR/"

"$PHP_BIN" artisan optimize:clear
"$PHP_BIN" artisan config:cache
"$PHP_BIN" artisan route:cache
"$PHP_BIN" artisan view:cache
"$PHP_BIN" artisan up
maintenance_enabled=false
curl --fail --silent --show-error --max-time 30 "$HEALTH_URL" >/dev/null

deployed_revision=$(git rev-parse HEAD)
printf 'Deployment completed: %s\n' "$deployed_revision"
printf 'Health check: %s\n' "$HEALTH_URL"

Strict mode: set -Eeuo pipefail stops the script when a command, variable or pipeline fails unexpectedly.

Error trap: if deployment fails after maintenance mode starts, the trap brings Laravel back online.

Preflight: file, branch and working-tree checks stop an unsafe release before it affects users.

Fast-forward check: production can move forward to approved main, but it cannot invent a merge or overwrite divergent history.

Release: Composer installs locked packages, Laravel applies only pending migrations, and rsync publishes public assets.

Verification: caches are rebuilt, maintenance mode ends and curl confirms the health endpoint responds successfully.

The script checks the environment, permits only a clean main branch, requires a fast-forward, enables maintenance mode, installs locked dependencies, runs pending migrations, publishes assets, rebuilds caches and performs a health check.

Use composer install, not composer update. Never put migrate:fresh, db:wipe, migrate:reset or automatic destructive rollback commands in the deployment script.

18

Create, bootstrap and run a release

Create the deployment feature

bash -n checks the script's syntax without running the deployment. git diff --check catches whitespace errors before review.

git switch develop
git pull --ff-only origin develop
git switch -c feature/git-deployment-workflow
bash -n deploy/shared-hosting-deploy.sh
npm run build
git status --short
git diff --check
git diff --stat
git add .
git commit -m "chore: add shared-hosting Git deployment workflow"
git push -u origin feature/git-deployment-workflow

Merge feature/git-deployment-workflow → develop, then develop → main.

First bootstrap deployment

The first release is special because the deployment script is not on the server yet. Inspect the incoming commits and files before performing the one controlled fast-forward.

cd <APP_DIR>
git fetch origin main
git --no-pager log --oneline HEAD..origin/main
git --no-pager diff --stat HEAD..origin/main

git merge --ff-only origin/main
git status --short
ls -la deploy/shared-hosting-deploy.sh
bash -n deploy/shared-hosting-deploy.sh
./deploy/shared-hosting-deploy.sh

Every routine deployment after that

After bootstrap, the operator needs only three commands: connect, enter the private application directory and run the guarded script.

ssh <SSH_USER>@<SSH_HOST> -p <SSH_PORT>
cd <APP_DIR>
./deploy/shared-hosting-deploy.sh

Do not run git pull first. Fetching and applying origin/main is the deployment script's responsibility.

21

Files that automatic deployment must preserve

  • <APP_DIR>/.env and <APP_DIR>/storage
  • Production database contents and user uploads
  • <PUBLIC_DIR>/index.php and <PUBLIC_DIR>/.htaccess
  • <PUBLIC_DIR>/storage symbolic link
  • Hosting-specific configuration

The document-root entry files may contain hosting-specific absolute paths. The rsync exclusions protect them.

Common deployment errors

Not a Git repository

Initialise Git, add the remote, authenticate, fetch main and use git reset --mixed origin/main.

GitHub asks for an HTTPS username

Cancel with Ctrl+C, create a read-only deploy key and switch origin to SSH.

Local changes block branch switching

Identify the exact file and use a path-specific stash. Do not discard unrelated work.

The terminal shows (END)

# Press q, or avoid the pager:
git --no-pager diff --stat develop main
export GIT_PAGER=cat

Production history has diverged

git status
git branch -vv
git --no-pager log --oneline --graph --decorate --all -30

These diagnostic commands show changed files, branch tracking and a visual history graph. They help you understand the divergence without altering it.

Resolve the history through the repository workflow. Never use git reset --hard as an automatic repair.

Maintenance mode remains enabled

cd <APP_DIR>
<PHP_BIN> artisan up

The health check fails

curl -i <PRODUCTION_URL>/health
tail -n 100 <APP_DIR>/storage/logs/laravel.log
git status
git log -1 --oneline
23

Use a reviewed, forward-safe rollback

  1. Identify the faulty pull request or commit.
  2. Create a revert commit locally or through GitHub.
  3. Review and merge the revert into develop, then main.
  4. Run the deployment script again.
git switch develop
git pull --ff-only origin develop
git switch -c bugfix/revert-faulty-release
git revert <FAULTY_COMMIT>
git push -u origin bugfix/revert-faulty-release
Revert is safer than erasing history

git revert creates a new commit that reverses an older commit. The original history remains visible, reviewable and recoverable.

Rolling application code backward does not reverse a database migration safely. Prefer a new corrective migration and verify a database backup before high-risk schema releases.

24

Security controls

  • Use a repository-scoped, read-only deploy key and protect it with chmod 600.
  • Keep .env, environment backups and deployment scripts outside the public document root.
  • Never log credentials, APP_KEY values, payment secrets, card data or private keys.
  • Deploy only main—never develop, feature or bug-fix branches.
  • Do not make unreviewed production source-code edits through FTP or SSH.
25

Routine release checklist

Local development

  • Started from the latest origin/develop
  • Used a dedicated feature or bug-fix branch
  • Reviewed git status and git diff
  • Built and committed frontend assets when required
  • Pushed a descriptive commit to GitHub

GitHub review

  • Merged the work branch into develop
  • Reviewed the integrated develop version
  • Merged develop into main
  • Confirmed main contains only approved production work

Production and verification

  • Ran the script from the private application directory
  • Fast-forward, Composer, migrations, assets and caches completed
  • Maintenance mode was disabled and the health check passed
  • Homepage, authentication, navigation and primary workflows work
  • No new production errors appear in the Laravel log

Final operating rule

All application changes begin locally, move through a feature or bug-fix pull request into develop, then through a release pull request into main. Production accepts only guarded, fast-forward updates from origin/main.

The server stores environment-specific configuration and persistent runtime data; it is not a development workstation. This separation keeps releases reviewable, repeatable and recoverable.
